## 2. 判斷移除原因（**以下為推測，標明依據**）

**先講查不到的部分**：上游 commit message 全是 `1` / `更新` / `Add files via upload`，沒有任何說明文字；
repo 內沒有 CHANGELOG／patch note；本次調查**未查證 GitHub issue／discussion**（沒有對外查詢）。
所以移除原因**只能從 code 演進推**，以下三條都是推論。

1. **`2d09dca77` 本身是一次大規模數值重平衡**，祝福／遠古改版只是其中一塊。
   同一 commit 裡頭目 HP 與金幣被大幅下修（例：黑長者 HP 12000→2500、`goldMin` 2452→245；古代巨人 HP 15000→8000）。

2. **設計方向是「隨機賭局 → 可規劃的養成」**。
   舊碧恩＝一張卷軸亂動三軸、可能把已有詞綴消掉；新碧恩＝玩家指定元素、階級單向往上、有 +10/+11 門檻、
   第 5 階還能附加魔法並升星（`js/11-world-map.js:979-1046`）。

3. **舊入口跟新屬性系統直接相衝**。屬性從「隨機 1/3/5 階」升級成 5 階制＋附加魔法＋星級之後，
   「一張卷軸三軸亂抽」會把玩家剛衝上去的 5 階洗掉——舊入口留著就是在破壞新系統。

**推測結論**：遠古不像是「被判定不好而廢止」，比較像**在把屬性抽出來做成獨立養成線時、順手把整個舊入口一起拆掉，
遠古剛好只掛在那個入口上，於是變成孤兒**。兩個佐證：

- 遠古的**消費端一行都沒動**（數值、名稱、顏色、四種光效、CSS、簽章、收購比對全在，見下節）——
  真要廢止的東西不會留這麼完整。對照組：席琳套裝詞綴停用時，上游有明確寫「不再出現於裝備上、既有裝備保留顯示但不計入」（`js/08-items-equip.js:128-130`），遠古沒有任何這種收尾註解。
- **世界頻道台詞到現在還在教玩家去找碧恩要遠古**（`js/26-world-channel.js:784-785`：
  「屬性跟遠古能力要找碧恩」「想洗那兩種就去象牙塔」）——v3.0.77 之後這句就不成立，上游沒回頭清。

## 4. 可行性結論（兩套分開講）

### 4.1 裝備祝福系統 → **純外掛可做**，不需核心補丁

需要的東西全部是全域函式或可變物件：

| 需要什麼 | 現況 |
|---|---|
| UI 掛點 | `renderBianAttr` 是 `js/11-world-map.js:1066` 的**頂層 function 宣告** → 在 `window` 上，可包。**已有先例**：`afk-attrbatch.js:198-208` 就是包它 |
| 寫值 | `player.eq[<slot>].bless = true` — 純欄位，存檔自然帶走 |
| 顯示與數值 | `blessName` / `blessColorClass` / `getItemFullName` / `applyBlessStats` 全在（`js/08-items-equip.js:406-413`、`:435`） |
| 收尾 | `calcStats` / `updateUI` / `renderTabs` / `saveGame` / `logSys` 全域 |

⚠️ **不能照抄舊版的兩個函式**：`pledgeCountItem`（數道具）與 `rollAttrAffix`（骰屬性）**現行版本都已不存在**。
數道具改用 `invCountId`（`js/14-craft-pandora.js:978`）或自己數；屬性軸建議根本不要碰（見 §5.2）。

### 4.2 遠古系統 → **純外掛可做，而且比祝福更單純**

消費端 100% 完整（§3.C），外掛只要提供「**寫入 `item.anc`**」這一個動作，
四變體的數值／名稱／顏色／光效／CSS／簽章／收購比對**一行都不必自己刻**。
不需要任何核心補丁。

### 4.3 為什麼兩套都不需要錨點式核心補丁

核心補丁只用在「外掛包不住」的四種情形（抽函式、改函式簽名、改寫死字面值、改核心熱點寫法）。
這兩套要動的只有：包一個全域 render 函式、寫一個存檔欄位、呼叫既有的全域函式——**四種都不沾**。

### 4.4 「加一個克里斯特 NPC 回來」— 可做但不建議

技術上可行（`DB.towns.town_ivory_tower.npcs.push(...)`＋`TOWN_NPC_POS_OVERRIDE`（`js/11-world-map.js:1993`）
＋包 `interactNPC`，否則不認得的 id 會掉進「🚧 系統建置中」分支 `js/11-world-map.js:1773`），但有一個不直觀的副作用：

> **`_npcSpriteKey`（`js/11-world-map.js:1883`）用 `usedSet` 在同一城鎮內去重**——
> 多插一個 NPC 會把後面 NPC 原本拿到的立繪擠掉，**象牙塔其他 7 位的長相可能整批換人**。

→ 建議**不新增 NPC**，功能直接掛在碧恩面板裡（也符合舊制：卷軸兌換歸克里斯特、施加歸碧恩，我們只做施加那半）。

### 5.1 檔案與掛接

**單一外掛 `afk-blessanc.js`**（不要拆成兩支——共用同一塊面板與同一套卷軸／消耗邏輯，

| 項目 | 內容 |
|---|---|
| 掛接方式 | 包 `window.renderBianAttr`，在 `el.firstElementChild` 的 `beforeend` 插自己的區塊（照抄 `afk-attrbatch.js:198-208` 那招） |

### 5.2 三個必須先拍板的規則決定（**不要照抄舊版**）

**① 卷軸／代價從哪來**

| 方案 | 作法 | 評價 |
|---|---|---|
| (a) 復活舊掉落 | 包 `killMob` 自己骰 40 等以上 BOSS 0.1%／0.1%／0.01% | ⚠️ 要跟 `afk-offline` 排順序，且**離線結算也得一起補**否則線上／離線收益不一致 |
| (b) 面板上直接花金幣／既有材料 | 完全不碰 `killMob` | ✅ **建議**：實作最乾淨，不碰離線那條熱路徑 |
| (c) 不給新來源，只讓舊存檔手上那幾張能用 | 只復活 `noUse` 那三張的用途 | ❌ 對絕大多數玩家等於沒做 |

**② 要不要照抄「三軸亂抽」→ 🚨 強烈建議不要**

舊版 1/3 機率動到屬性軸，而且「同軸同值→消除」。在現行 5 階屬性制下，
**一次點擊就可能把玩家辛苦衝上去的 5 階＋★3 附加魔法洗成隨機低階**。
何況 `rollAttrAffix` 已不存在，照抄等於**我方擅自重新定義上游的屬性規則**。

→ 只做「祝福」與「遠古」兩顆各自獨立的按鈕，**完全不碰 `item.attr` / `item.attrMagic` / `item.attrMagicStar`**。

**③ 要不要放詛咒進來 → 建議不要**

舊版祝福軸 50% 出詛咒。詛咒裝備無法卸下（`js/08-items-equip.js:1069`），
而詛咒目前在遊戲裡**沒有任何來源**（§3.B）→ 放回去等於我方單方面新增一個負面狀態。
要保留賭博感，用「失敗＝只消耗代價、裝備安然無恙」就好（比照現行碧恩 7% 的寫法）。

### 5.3 UI（照 `CLAUDE.md` 的版面預算）

- 面板說明 **≤1 句**；部位下拉 ＋ 兩顆按鈕，按鈕名稱本身就要說清楚在做什麼
- 成功／失敗各 **1 句** `logSys`，沿用核心既有的顏色 class（`c-blessed` / `c-ancient` 等）
- **不要**在畫面上寫「這三張舊卷軸已無用途」「遠古系當年怎麼被拿掉的」這類說明——玩家看了也不會有不同動作

### 5.4 驗證（上線前必做）

- 用 `.testdata/` 的**真實存檔**灌進去 → 操作 → 比對 `lineage_idle_save_N`：只有目標那件的 `bless`/`anc` 變了，其餘 key 沒被動到
- 涵蓋「主選單／未載入角色」狀態：確認外掛載入時不會盲呼叫 `saveGame()`（本 repo 踩過，把第 1 格蓋成 Lv.1 null）
- headless Playwright 跑一輪 smoke（含手機那兩輪）

### 6.2 上游哪天自己做回來

撞車面：`renderBianAttr` 的內容、`new_item_bless_*` 三個 id、`item.anc` 欄位。
上游若自己補一套，會變成兩個入口同時存在（面板兩塊、規則兩份）。

緩解：

1. 外掛**預設關**（`def:false`）
2. 載入時偵測「上游是否已有自己的入口」→ 有就 `console.warn` 後自我停用。
   **判準用函式存在性**（例如 `typeof doBianAnc === 'function'`），
   🚨 **不可以比對 `renderBianAttr` 的 HTML 內容**——那是對上游原文的假設，作者改一個字就失效
3. 每次同步上游後人工掃一次碧恩面板（`docs/plugins.md` 已有同類提醒）

### 6.3 舊存檔殘留資料

- **不需要處理，也不應該處理**：舊存檔的遠古裝備現在就正常生效（§3.C），我們什麼都不做它也活著。
- 三張死卷軸躺在背包：選 (a) 會讓它們突然可用（對舊玩家是意外之財，量小、影響有限）；
  選 (b) 則維持死道具，面板上**不要提到它們**。
- 🚨 **絕對不做「掃描存檔幫玩家清理／轉換舊詞綴」**——那是「認得被搬內容」的操作，`CLAUDE.md` 明文禁止，
  而且會在玩家換裝置／上游改欄位時才爆。

### 6.4 平衡

- **祝福的裝備賣價 ×10**（`js/10-ui-tabs.js:1817`）→ 可任意施加祝福＝金幣印鈔機。
  緩解：代價要壓過賣價差；並沿用舊版「只能對**裝備中**的施加」（天然限流：一次只有一件在那個部位）。

## 7. 建議結論：先許願給上游，沒動作再自己做，且只做遠古

**理由（三條，按份量排）**

1. **這不是我方缺功能，是上游自己留下的半截工程。**
   遠古的消費端一行都沒少（數值／顏色／光效／CSS／簽章／收購比對全在），只有產生端被 v3.0.77 順手拆掉；
   世界頻道到現在還在教玩家去找碧恩要遠古（`js/26-world-channel.js:784-785`）。
   這種「大概率是漏掉、不是刻意廢止」的東西，先問一句比自己做划算——
   作者本來就打算補回來的話，我們自己那份會直接撞車。

2. **祝福那半，我方做的正當性最弱。**
   祝福詞綴現在照樣拿得到（掉落 1%、頭目／製作 10%、席琳頭目 20%／瘋狂 30%、傳家之寶 10%、製作傳承），
   少的只是「指定施加」——那是**難度設計，不是壞掉**。
   我方擅自加一個能指定祝福的入口，等於改動上游的養成節奏，還踩到 ×10 賣價這個金幣出口。

3. **遠古那半，如果上游不打算做，我方自己做是合理的。**
   它是純孤兒，做回來不跟任何現行系統打架，外掛層完全包得住、預設關、玩家一鍵就能還原成原版。

**建議順序**

1. 先發一則許願給原作者，附**兩個具體事實**（比純許願有說服力）：
   ① 遠古的消費端完整還在（`applyAncStats` / 顏色 / 光效 / CSS 都沒動），只缺一個入口；
   ② 世界頻道 `affix` 條目的台詞從 v3.0.77 起就過期了，還在叫玩家去找碧恩要遠古。
2. 等一到兩次上游改版。作者沒動作，再排我方實作，範圍收斂成：
   **只做遠古、不做祝福、不做詛咒、完全不碰屬性軸**，代價走金幣／既有材料（§5.2(b)），預設關。
3. 真的做了，記得同步改 `afk-wiki.js:780`、`:798`（跑 `/update-wiki`）與 `docs/plugins.md` 的外掛表。
